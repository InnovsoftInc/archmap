# How to record a change

The map is the source of truth for this project's architecture: categories, services and their parts, connections, database tables, columns, enums, personas and flows. Changes are recorded as **saves**, reviewed in pull requests, and published as **versions** (usually one per sprint).

## What belongs on the map

Record what someone joining the project needs in order to understand how it
fits together. Leave out how each piece is written inside. The map has four
layers; put each change in the layer it belongs to.

1. **Overview**: every app or service the project deploys, every database,
   queue or file store, every outside service it calls (sign-in, email,
   payments, AI, hosting), and the connections between them. Update it when
   one of these is added, removed, replaced or moved.
2. **Parts**: inside each app, every endpoint it serves (method and path), every
   background or scheduled job, and every storage container (bucket, queue,
   topic). Libraries and tools only when they shape the architecture: the
   framework, auth, database access, payments, messaging, observability. Not
   general utilities.
3. **Data**: every table and column in the databases the project owns, and every
   enum they use. Not indexes (except unique constraints), migrations or views.
4. **People and flows**: one persona per kind of user the product serves (the
   roles in its auth, or the people a brief names), what each needs to get done,
   and the main journeys through the services: signing up, the product's core
   jobs, paying. Not every screen or click.

Record a change when code adds, removes, renames or rewires one of these, or
when a decision is made about one that isn't built yet (`status: planned`), or
is being phased out (`status: retiring`). A refactor, a test, or a change
inside a file that leaves all of the above as it was needs no save.

Never put on the map: secrets, keys, tokens, passwords or environment values;
personal data; internal hostnames or URLs that include credentials; UI
components, helper functions, test fixtures or one-off scripts; anything that's
only an idea nobody has decided on.

## Where things live

All of it is in the `architecture/` folder:

- `saves/<id>.json`: one file per save, a batch of related changes. Never edit or delete a save once it's merged. Fix a mistake with a new save that says so.
- `versions.json`: published versions. Saves in no version form the **draft**.
- `current.json`: the latest state, generated by `archmap snapshot`. Read it to see what exists; don't edit it.
- `archmap.config.json`: name, logo, colours and labels.

## Record a change

1. Read `current.json` (run `archmap snapshot` first if it's stale) and find every id you'll touch. For update or remove, the id must exist; for add, it mustn't.
2. Run `archmap save --summary "Add status to orders" --author "Name via Claude"`, then fill in the new file's `ops`:

```json
{
  "at": "2026-11-20T18:04:00Z",
  "author": "Name via Claude",
  "summary": "Add status to orders",
  "ops": [
    {
      "kind": "column",
      "id": "orders.status",
      "op": "add",
      "value": {
        "type": "text",
        "enum": "order_status",
        "after": "total",
        "desc": "Where the order is in fulfilment."
      },
      "reason": "Support needs to see whether an order has shipped without asking the warehouse."
    }
  ]
}
```

3. Run `archmap check`. Fix anything it reports, then open a pull request.

## Kinds, ids and values

- **category**: id like `backend`. `{ name, order, purpose, external }` (`external: true` sits outside the platform boundary).
- **service**: id like `api`. Anything in a category: an app, database, job, outside service, or a part of another item. `{ name, lane: <category id>, parent: <service id, for parts>, type: app | store | job | platform | external | group | endpoint | module | library | tool | container, tech, purpose, status: live | in build | planned | retiring | external, facts: [{ k, v }], notes, docs: [{ label, url }], opens: "schema" (the database), order }`.
- **connection**: id `from->to`. `{ from, to, label, protocol, status }`.
- **area**: id like `identity`; groups tables. `{ name, order, row, cols }`.
- **table**: id = table name. `{ area, purpose, append, order, columns: [...] }` (columns only on add).
- **column**: id `table.column`. `{ type, pk, unique, fk, enum, array, desc, after }`.
- **enum**: id = enum name. `{ values: [...], style: native | check }`. Add it before a column that uses it.
- **persona**: id like `operator`. `{ name, kind, who, blurb, subtypes, uses: [{ to, label }], jobs: [{ job, t: { table: r | w }, gap, fix, open, note }], order, source }`.
- **flow**: id like `operator_renews`. `{ name, description, order, steps: [{ from, to, label, status }] }`; `from` and `to` are service ids or `persona:<id>`, and each step must follow a recorded connection or a persona's use.

## Rules

- `update` merges the fields you give; lists (columns, values, jobs, docs, steps) are replaced whole.
- Removing something also means removing or updating what points at it; `archmap check` lists anything left dangling.
- Renames: remove the old id and add the new one in the same save.
- Every op needs a `reason` a teammate understands without the conversation, plus the ticket or PR if there is one.
- One feature or decision per save. Record real things: mark anything not built yet `status: planned`.
- Plain English in summaries and reasons.

## Publish a version

At the end of a sprint: `archmap publish "Sprint 2" --summary "What this sprint changed"`, then merge the PR. The map opens on the newest version.
